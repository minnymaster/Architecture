## 2. Диаграмма контейнеров

### 1. Акторы/Пользователи:
  - Директор компании - стратегическое управление
  - HR-специалист - оперативное управление процессами
  - Сотрудник компании - основной пользователь системы

### 2. Веб-приложения(клиентские интерфейсы):
  - Консоль директора - аналитика и отчеты
  - Консоль HR-специалиста - управление и настройка 
  - Консоль сотрудника - обучение и аттестация

### 3. API Gateway:
  - Analytics API Gateway - доступ для аналитических данных
  - Manage API Gateway - доступ для управления и модификации данных, настроек системы
  - Learning API Gateway - доступ для обучающих материалов, тестирования

### 4. Бизнес-сервисы:
  - Reports API - формирование отчетов 
  - Dashboard API - агрегированные данных и формирование аналитических отчётов
  - Courses API - получение данных курсов, содержания, количество
  - Management API - администрирование
  - Tests API - проведение тестирования

### 5. Базы данных:
  - Company Database - хранение данных обо всех сотрудниках, прохождение курсов, результаты аттестаций
  - Certifications Database - база данных всех накопленных знаний о предмете аттестации
  - Courses Database - хранение всего список курсов и всех данных курсов

### Выбранная архитектура: Микросервисная архитектура с ролевым разделением и CQRS-элементами
Обоснование выбранной архитектуры:
  1. Соответствие бизнес-доменам. Каждый сервис отвечает за четкую бизнес-способность:
  - Tests API → проведение аттестаций
  - Courses API → управление обучением
  - Management API → административные функции
  - Reports API → аналитика и отчетность
  - Dashboard API → визуализация данных

  2. Разделение по типам пользователей через API Gateway:
   - Manage API Gateway → только управляющие операции (HR)
   - Learning API Gateway → только обучение и тестирование (сотрудники)
   - Analytics API Gateway → формирование отчётности, является исключением, так как доступ к отчётности требуется на разных уровнях доступа всем видам пользователей(HR, сотрудники, директор)

### Обоснование разделения на 3 базы данных:
1. Company Database
- Назначение: операционные данные сотрудников, курсов, результатов
- Почему отдельно: чувствительные персональные данные, требующие строгой безопасности
- Используют: Reports API, Dashboard API, Management API

2. Certifications Database
- Назначение: доменные знания, вопросы тестов, компетенции
- Почему отдельно: стабильная структура, интеллектуальная собственность компании
- Использует: Tests API

3. Courses Database
- Назначение: обучающие материалы, медиаконтент, документы
- Почему отдельно: большие объемы данных, специфичные форматы хранения
- Использует: Manage API, Courses API

### Ключевые архитектурные решения:
1. Выделение Tests API в отдельный сервис
- Причина: самый нагруженный компонент системы
- Обоснование: требование времени отклика ≤2 секунд при 20 одновременных пользователях

2. Разделение Reports API и Dashboard API
- Причина: разные паттерны использования данных
- Обоснование: отчёты требуют информацию об оперативных данных в относительно небольших объёмах, которые не требуют визуализацию. Дашборды в свою очередь оперируют большими объёмами данных, агрегируют их и визуализируют, что требует гораздо больше ресурсов.

3. Три специализированные БД
- Причина: разделение ответственности и оптимизация
- Обоснование: избежание конфликтов между операциями, изоляция персональных данных, независимое масштабирование хранилищ


### Преимущества выбранной архитектуры:
- Отказоустойчивость: сбой в одной БД не ломает всю систему
- Производительность: оптимизация каждой БД под конкретные нагрузки
- Безопасность: минимальные привилегии для каждого сервиса
- Поддержка: разные команды могут работать с разными компонентами
- Масштабируемость: легкое добавление новых функций (например, LLM-интеграции)
